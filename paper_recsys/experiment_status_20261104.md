## 先看这三句

1. **方向继续做。** 数据处理、time-split protocol、文本特征、复现框架和实验记录都可以接着用。不另起一个完全不同的大模型课题。

## 二、下一轮主问题

收成这一句：

> 在时间一致的推荐 evaluation 下，什么样的文本视角真正带来了额外的任务信息，什么样的只是增加了表示差异和计算成本。

两条路线，**先做第一条，用结果决定第二条开不开**：

| 路线 | 内容 | 什么时候做 |
|------|------|------------|
| A. 机制型实证 | 用受控干预把「视角怎么构造、怎么编码、时间 evaluation 各自起什么作用」分开，给出适用边界 | **先做** |
| B. 轻量使用规则 | 在 A 的结果上，提出一个可验证的视角选择或使用规则 | 仅当 A 的证据支持时再开 |

路线 B 不要求复杂网络。把已有 gate 换个名字不算。

负结果的标准也改了：不能预先认定「MV 不如 TF-IDF」本身就够投稿。需要的负结果必须能被检验、能排除其他解释，并且对后续研究有用。为了凑一个新方法，不要把 SE、Cross、boost 加回来。

## 三、四位审稿人：各自要什么，落到哪一阶段

| 审稿人 | 真正在问的事 | 落到 |

| **R2** | 结论的分量和稳定性。几个方法数值接近时，不能只凭均值排序说谁更 robust。差异的不确定性、适用范围、实际价值都要交代。 | 阶段 3 的分层；阶段 4 的配对差异和置信区间 |

| 3. Evaluation 锚点 | 固定 checkpoint 上的 Successive，以及相对 TF-IDF 的分层增益 | Last 与 Random 排序不同，是目标构成能解释，还是分层后仍在 | 未开始 |
| 4. 有限外推 + 定稿决策 | 非 Amazon、第二 encoder、一个外部方法；然后决定写机制论文、试轻量规则，还是收窄 | 相比上一版排除了什么解释，新增了什么可迁移的认识 | 未开始 |

### 阶段 1 — 冻结现有版本，做有边界的实验审计

这一步**不是把所有实验重跑**。目的是确认后面的比较站在同一套实现上。

先把下面五样对齐，写成一张对应表：

- 当前论文版本
- 代码 commit
- 数据划分
- 特征文件
- 主表结果

重点核查三件事：

1. **Early 的特征统计是否只在 Early cutoff 之前拟合。**
2. **Last / Random / Successive 是否用同一套历史构造和候选规则。**
3. **各模型的 alignment、融合容量、训练开关是否确实相同。**

Seed 规则提前写死：

- 随机 seed 列表事先固定。
- 某个 seed 结果不理想，或方差大，**不能**因此删掉。
- 只有明确的程序故障，才能按事先约定的规则排除，并且保留 log。

已经反复看过的测试结果，可以继续用来探索和复盘。后面要写进论文的关键 claim，在协议冻结之后，放到**新的时间窗口或外部数据**上再确认一次。

**产出：** 一份短的 experiment protocol，加上能够自动运行的检查脚本。  
**通过之后：** 冻结。不因为某一组指标不好看就改协议。

### 阶段 2 — 先做最能区分原因的小实验

优先问题：prompt 是否真的产生了不同的信息视角。

按论文现在写的流程，做法是：不同的问题式 prompt 与**同一份商品文本**拼接，再读 hidden states 做 pooling。并不是先得到四份内容不同的回答，再分别编码。因此现在的高相似度可以来自共享文本、prompt 改动有限、pooling，也可以与 encoder 有关。现有证据分不开这些原因。

在 **Beauty** 上做小规模试验：

| 臂 | 做什么 |
|----|--------|
| 保留 | 当前问法式视角 |
| 新构造 | 基于原始文本、实际改变内容组织方式的视角，例如属性、功能、适用对象的信息抽取 |
| 抽取约束 | 内容必须能追溯到原文；原文没有的信息允许为空；不为了凑齐四个 view 让大模型编造 |
| 对照维度 | 再加入一个不同来源的 encoder，形成小型的 encoder × 视角构造方式对照 |

运行顺序，避免一次把格子跑满：

1. 先检查编码是否符合各自模型的使用方式，表示分析是否可信。
2. 再选**最能区分假设**的 config 进入推荐训练。
3. 不要一开始就对全部组合跑多 seed。
4. 若要查 pooling：同一个 encoder、同一份输入，只改 pooling。不要同时换 encoder、输入和融合结构。

另留一个便宜对照：把**同一份 single-view 特征重复**成相同数量的分支、相近的容量。开跑之前写清楚两种结果分别意味着什么：

- 真正的四视角**不优于**重复视角 → 意味着什么
- 真正的四视角**优于**重复视角 → 意味着什么

**Stop 条件不是「MV 终于赢了」。**  
停的标准是能回答：目前的问题更接近输入视角重复、编码方式不合适，还是确实没有稳定的额外任务信息。三种结果对应三种论文结论，不再维护原来的方法层级。

### 阶段 3 — 让 Last / Random 的差异有明确解释

设定：

- 保留固定 checkpoint，权重不更新。
- 在固定用户样本上补 **Successive**。
- 每个事件只用当时已经发生的历史。
- 从**同一批事件**计算 Last、Random 和逐事件表现。

需要先讲清楚的关系，而不是先判谁对谁错：

- 相同事件集合、相同过滤、相同用户权重下，Random 是「用户内平均事件表现」的一种抽样估计。
- Last 关注窗口里的最后一个事件。
- 两者排序不同，不自动说明其中一个错了或有偏。
- 先明确部署时究竟想预测什么。《Time to Split》把 Last、Random、Successive 看成不同但有联系的 evaluation 选择，不是要求所有场景只有一种正确答案。

然后比较：文本方案相对 TF-IDF 的增益，是否随下面四项变化。

- 事件位置
- 距 cutoff 的时间
- 用户历史长度
- 目标 item 频次

这是用来回答「为什么 Last 与 Random 会偏向不同方法」。不要只画 score entropy 或集中度，再从图倒推故事。

结果怎么写：

- 差异主要由目标构成解释 → 把构成效应讲清楚。
- 分层之后仍然存在 → 如实报告还有未解释的部分。
- warm-only 的范围继续写明。
- 不为了补这一点，临时加一套零交互推荐系统。

### 阶段 4 — 有限外推，再决定要不要轻量方法、怎么定稿

**数据：** 优先补一个带可靠时间戳和文本的**非 Amazon** 场景，而不是第四个 Amazon category。

**方法对照保留四行：** ID-only、TF-IDF、single-view、multi-view。  
再从审稿人提到的 LLM-Rec、SC-Rec 等工作里，按**输入、输出、训练设定**选一个最相关的外部 baseline。

- 先读原文，再实现。
- 若为了能跑而改了主要输入或训练流程，不能写成该方法的完整复现。
- 改编的部分明确标注。

**正式结果的统计口径：**

- 事先固定的 seed，相同的调参预算。
- 保留逐用户或逐事件输出。
- 报告配对差异和置信区间。
- 「落在一个 std 内」不是等价证明。
- 一个很小的 p 值也不是「实际收益已经足够大」的证明。

做完之后按结果分叉，三选一，不并行铺开：

| 若结果是 | 则 |
|----------|----|
| 单看 CKA 或 effective rank，预测不了某个 view 有没有下游收益；但验证集上的边际收益或稳定性可以用来判断 | 可以研究一个**低成本视角选择规则**。这仍是待验证的 idea：先查相关工作，再和「随机选 view、按几何多样性选 view、固定 single-view、使用全部 view」比较。在此之前不称为新方法。 |
| 没有形成有价值的选择规则，但干预实验说清了多视角在什么条件下有用、什么条件下无用 | 继续走**机制型实证论文**。 |
| 只是又确认了一遍：某个 Qwen 的四个 prompt 不如 TF-IDF | **控制投入**，收窄论文和目标刊会。不再强冲同等级会议，避免继续堆租卡成本和时间。 |

**写作可以同步，但锁定顺序固定：**

1. 先写问题、实验设计和相关工作。
2. 摘要和贡献点等证据稳定后再锁。
3. 定稿前必须能写出这一句：**相比上一版，排除了什么解释，新增了什么可迁移的认识。**
4. 这句话写不出来，就还不适合靠语言包装准备下一次投稿。

## 五、实验怎么交给 AI 做

老师的背景说明：第九期小班时，Agentic AI 工具还不成熟，课上没有着重讲。老师认为工作里已经在用 AI 编程，科研上也按这个来提速。Codex 读 `AGENTS.md`，Claude Code 用 `CLAUDE.md`、hooks 和权限控制，把反复做的实验收成项目规则，不用每次向聊天模型重讲整个项目。

可以借鉴 autoresearch 的循环：**固定 evaluation 边界 → 限定修改范围 → 运行 → 记录 → 保留或回退。**  
不要把它的目标一起搬过来。原项目是在固定预算下把验证指标往上推；这边不能跑到「出现期待的模型层级」为止。

实际顺序固定为：

```text
研究假设
  → 人工批准实验卡片
  → AI 实现
  → 自动检查
  → 小样本试跑
  → 批准正式运行
  → 保存全部结果（含失败、下降、无增益）
  → 独立审计
  → 人工决定结论
```

每张实验卡片只写这些，并且必须能检查做完没有：

- 要回答的问题
- **唯一**主要改动
- 哪些文件不能动
- 比较对象
- 预算
- 验证指标
- 什么结果支持假设，什么结果反驳假设

不给 agent「把论文改得更强」这类任务。

项目文件保持少。三处就够：

| 文件 | 放什么 |
|------|--------|
| `AGENTS.md` / `CLAUDE.md` | 共同规则 |
| 研究计划 | 假设和实验优先级 |
| 实验登记表 | commit、config、seed、cutoff、特征文件 hash、checkpoint、结果路径 |

论文里每一张表都要能从登记表重新生成。

### 结果可信：这几条不能只写在 prompt 里

老师点名：即便比较强的模型（原文举例 Opus 5.5）仍会幻觉。下面几条要落在权限、分支和脚本上。原文这一句停在「不能只靠在 prompt 里写一句『请遵守』」，没有写完后半句；结合同一段里的 hooks 和权限控制，执行时按机械约束来做，而不是再补一句提示词。

1. **原始数据、split manifest、正式 evaluation 脚本**，实验 agent 不能随意改。涉及它们的修改单独审查。
2. 探索阶段不给 agent 自由读取已经确认的 test 结果。
3. 每个实验用独立分支或工作目录。多个 agent 不同时改同一套代码。
4. 失败、下降、无增益的 run 同样保存。不只留成功的。

## 六、写作：事实和句子分开，防幻觉，也防写弱

老师指出，之前论文大量由 AI 写和改，下一轮要把实验事实和语言表达分开管。

已经出现过的事实错误，下一轮默认禁止再犯：

- 把 valid 写成 test
- 把 GTS-All 混入 Last
- 修改 seed
- 引用放错位置

**先锁定、AI 不能默认改的东西：** 实验数字、protocol、citation、模型版本、贡献范围。  
AI 可以改句子，但没有修改这些事实的权限。

每次只改一个章节。输出四列：原句、改句、修改理由、对应证据。人工看 diff。没有来源的判断标成「待核查」。不允许为了段落顺而自动补一个解释。

### 过度防御

前一轮为了防 overclaim，反复要求 AI 更谨慎，结果把已有证据、有一定原创性的内容也写弱了。Abstract 和 Introduction 里反复出现这类句子时，读者看不到作者做成了什么：

- 「我们没有提出新模型」
- 「我们只是观察到」
- 「虽然范围有限」
- 「不能说明什么」

要分开两件事：没有依据的确定性必须降下来；研究价值不要无必要地降下去。证据缺口仍要补。真正影响结论的局限保留，并且写在相关结果旁边，不要全部堆到文末。

老师给的替换例子：

| | 句子 |
|--|------|
| 写弱了 | 我们没有提出新的架构，只进行了一项范围有限的实证研究。 |
| 改成 | 我们在共享推荐 backbone 下控制文本输入和 evaluation 目标，quantify 它们对方法比较的影响。随后写明测试了哪些数据、encoder 和场景。 |

后一句没有多承诺任何结果，但把已经做成的工作放在前面。

让 AI 改之前，先给一份 **贡献–证据–边界** 表：

| 格子里是 | AI 可以做的 |
|----------|-------------|
| 已有证据支持的 claim | 不许擅自删弱 |
| 尚未验证的解释 | 不许写成事实 |
| 真正影响结论的局限 | 必须保留，并放在相关结果附近 |

Audit 和表达分两轮，不要让模型始终站在否定作者的位置上改：

1. 一轮只找漏洞。
2. 一轮只查已证明的贡献有没有被写丢。
